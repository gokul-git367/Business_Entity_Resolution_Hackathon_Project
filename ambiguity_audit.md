# Training Dataset Ambiguity Audit

## 1. Purpose

This report audits the ambiguity categories listed in `Abiguity.txt` against the provided training dataset:

- `dataset/train/train_source1.tsv`
- `dataset/train/train_source2.tsv`
- `dataset/train/train_source3.tsv`
- `dataset/train/train_ground_truth.tsv`

The goal is to identify which risks are actually present, explain why they matter for entity resolution, and define the next measurements needed before building the matching pipeline.

### Status definitions

- **Present**: the pattern is visible in the training records or labels.
- **Not observed in training**: a full scan found no evidence, but this does not guarantee the pattern cannot occur in test data.
- **Uncertain**: the pattern needs a more specific labeled-pair or semantic analysis before it can be confirmed.

Important distinction: finding a pattern in the data does not prove that two records with that pattern represent the same business. Identity claims must be checked against `train_ground_truth.tsv`.

## 2. Executive Summary

The training data is a genuinely noisy multilingual entity-resolution problem. The most important confirmed difficulties are:

1. Native Indian scripts, mixed scripts, transliteration, accents, zero-width characters, and Unicode variation.
2. Typos, malformed tokens, token joining/splitting, punctuation variation, word reordering, and repeated tokens.
3. Legal suffix variation, abbreviations, DBA/trade names, aliases, and domain-like names.
4. Partial, reordered, landmark-based, numeric, and missing addresses.
5. Shared names and shared addresses that create false-merge risks.
6. Zero-match, one-match, and many-match relationships in the ground truth.
7. Source-specific and region-specific corruption patterns.
8. Compound corruption where several of these problems occur in the same record.

The solution should therefore compare name and address separately, retain multiple candidate-generation routes, use source-aware normalization, and prefer precision when evidence conflicts. Missing information should be treated as unknown, not as a contradiction.

## 3. Evidence Snapshot

The initial training audit found the following representative evidence:

| Area | Training evidence | Implication |
|---|---|---|
| Scripts | Devanagari, Tamil, Malayalam, Telugu, Gujarati, Kannada, Bengali, Latin, and mixed-script fields | Script detection and script-aware normalization are required. |
| Unicode | Accents, zero-width characters, combining/spacing variants, and non-ASCII punctuation | Normalize Unicode and remove invisible formatting carefully. |
| Names | Typos such as `Tetlecommunication`, `Hospirlg`, and `Hurricanne` | Character-level and token-level similarity are both needed. |
| Tokenization | Joined forms such as `Roadvellakinar`, `Kapilcomplex`, and `Doorno` | Token boundaries cannot be trusted. |
| Legal forms | `Pvt`, `Ltd`, `LLC`, `Inc`, `Corp`, duplicated suffixes, and reordered suffixes | Model the legal suffix separately from the core business name. |
| Aliases | `dba`, `d/b/a`, `fka`, domain names, and social-style handles | Exact name matching will miss some true matches. |
| Addresses | Blank fields, landmarks, reordered components, numeric identifiers, and partial addresses | Compare address components and tolerate missing information. |
| Entity structure | Empty, singleton, and multi-target ground-truth rows | Matching must support zero, one, or many target records. |
| Sources | Source 1 is generally cleaner; Sources 2 and 3 have distinct corruption patterns | Use source-specific features and thresholds. |

The counts reported in the first audit are lower bounds where indexed search limits applied. Exact totals should be generated by the streaming audit described in Section 6.

## 5. Highest-Priority Risks

### 5.1 False merges

The most dangerous false-positive patterns are:

- Common or short names combined with shared roads, landmarks, or cities.
- Exact or near-exact names with conflicting addresses.
- Same address with different businesses in the same building or locality.
- Generic legal suffixes treated as identity-bearing tokens.
- Placeholder or missing fields interpreted as positive evidence.
- Acronyms, DBA names, and corporate-family names merged without context.

Because evaluation uses precision-heavy macro $F_{0.5}$, a conservative decision threshold is appropriate for ambiguous candidates.

### 5.2 Missed matches

The most dangerous false-negative patterns are:

- Native script versus Latin transliteration.
- Joined or split tokens.
- Multiple typos in the same name.
- DBA or alias names with little literal overlap.
- Missing addresses where the name is the main available evidence.
- Reordered address components.
- Source-specific corruption not handled by a global normalizer.

Candidate generation must be more permissive than final matching. A match lost during blocking cannot be recovered by the classifier.

## 6. Recommended Analysis Implementation

Use a streaming audit script over the training files. The audit should write a compact result table rather than retaining all source rows in memory.

### 6.1 Input validation

1. Read each file with an explicit tab separator.
2. Verify expected columns and source ID prefixes.
3. Count malformed rows and unexpected column counts.
4. Count duplicate entity IDs within each source.
5. Parse the ground-truth comma-separated target lists.
6. Verify that every ground-truth target exists in Source 2 or Source 3.
7. Verify that every Source 1 ID occurs once in ground truth.

### 6.2 Text and script detectors

For every name and address field, calculate:

- Raw length and normalized length.
- Token count before and after normalization.
- Unicode normalization delta.
- Zero-width/control-character count.
- Whitespace and non-breaking-space count.
- Digit count and digit-token patterns.
- Punctuation and symbol count.
- Unicode-script block counts.
- Mixed-script flag.
- URL/domain, DBA, FKA, and alias-marker flags.
- Legal-suffix and address-abbreviation flags.
- Placeholder/missing flag.

Summarize all detectors by source and country.

### 6.3 Ground-truth pair analysis

For every labeled S1-to-S2 or S1-to-S3 pair, calculate separate name and address features:

- Exact raw and normalized equality.
- Character n-gram similarity.
- Edit similarity.
- Token Jaccard and weighted token overlap.
- Script overlap and transliteration-aware overlap.
- Legal-suffix-stripped name similarity.
- Numeric-token overlap.
- Postal/PIN agreement.
- Address-component overlap.
- Missingness and field-quality indicators.

For sampled nonmatches, use hard negatives such as same normalized name, same postal code, same city, same address, or shared generic tokens. Compare true and false pair distributions.

### 6.4 Entity-structure measurements

Compute exact distributions for:

- Number of ground-truth targets per S1.
- S2-only, S3-only, and mixed-source matches.
- Maximum targets per S1.
- Number of S1 entities with no match.
- Repeated names across different S1 entities.
- Repeated addresses across different S1 entities.
- Same-name/different-address and same-address/different-name groups.
- Duplicate and near-duplicate rows within each source.

### 6.5 Blocking recall experiment

Evaluate several blocking routes independently and in union:

1. Normalized core-name key.
2. Character n-gram retrieval.
3. Rare-name-token retrieval.
4. Postal/PIN and numeric-address retrieval.
5. Locality/city/state/country retrieval.
6. Transliteration-aware retrieval.
7. Source-specific normalization variants.

For each route, report:

- Candidate count.
- Reduction ratio.
- True-match recall.
- Average candidates per S1.
- Recall by source, country, and ambiguity category.

The union of blocking routes should be used as the model candidate set if it meets the resource budget.

## 7. Recommended Matching Strategy

1. Normalize text in multiple views: raw, Unicode-normalized, punctuation-normalized, and transliteration-aware where available.
2. Keep name and address representations separate.
3. Extract the core business name after removing only recognized legal suffix structures.
4. Preserve numeric address tokens, postal codes, and unit identifiers.
5. Add source and country interaction features without restricting country values.
6. Score name evidence, address evidence, and contradiction evidence separately.
7. Use conservative thresholds for short names, common names, shared addresses, and alias-like records.
8. Allow multiple matches when the labels and evidence support them; do not force one-to-one matching.
9. Optimize thresholds on a validation split using macro $F_{0.5}$, including singleton rows.
10. Produce `candidate_pairs.tsv` from the final candidate set sent to the model, and ensure every final match is included there.

## 8. Limitations

- The first audit used indexed inspection for representative evidence; exact category counts should be produced by the streaming implementation in Section 6.
- Training cannot directly prove how unseen France records will be formatted.
- String evidence alone cannot establish parent-company, subsidiary, relocation, or semantic DBA relationships.
- The submission validator checks structure and ID constraints, not ambiguity quality, blocking recall, or matching accuracy.
- External lookup is prohibited, so geographic and business knowledge must not be imported from outside the supplied data.
